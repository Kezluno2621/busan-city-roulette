# 추천 기능 개편 전후 비교

## 변경 이유

기존 화면은 출발지 선택 → 단일 장소 추천 → 코스 룰렛을 순서대로 보여 주어, 서로 다른 추천 기능이 한 흐름처럼 보였다. 또한 선택 카테고리가 DB 조회의 배타 필터로 사용되어 음식점을 선택하면 음식점만 후보가 되는 문제가 있었다.

| 구분 | 변경 전 | 변경 후 |
|---|---|---|
| 진입 구조 | 3단계 강제 흐름 | 즉흥 룰렛 / 맞춤 코스 두 독립 기능 |
| 즉흥 추천 | 출발지 필수, 최근 결과 미반영 | 출발지 선택, 최근 30개 결과 우선 제외 |
| 카테고리 | 선택값만 DB에서 조회 | 선호 / 필수 포함 / 선택 유형만 |
| 후보 풀 | 코스 생성 상위 20개 | 최대 200개 + 누락된 역할의 소량 표본 활용 |
| 재현성 | seed 지원 | seed 지원 유지, seed 사용 시 최근 기록을 무시 |
| 저장 | 코스 결과 저장 | 두 기능 결과 모두 기존 저장 토큰 사용 |

DB 스키마와 기존 REST 경로는 변경하지 않았다. 기존 `POST /recommend`, `POST /api/recommendations`, `POST /api/courses/generate`도 유지한다.

## 반복 결과의 실제 원인

1. `RecommendationCandidateFilter`가 카테고리를 항상 배타적인 DB 조건으로 전달했다.
2. `CourseGenerationService`가 상위 20개 후보만 사용했다.
3. 브라우저와 서버 모두 직전 추천 장소를 다음 요청에 전달하지 않았다.
4. 높은 추천 점수에 선택 확률이 집중되었다.

실제 demo DB는 관광지 226건, 음식점 144건, 쇼핑 16건, 문화시설 1건 등으로 편중되어 있고 카페 분류가 0건이었다. 따라서 기본 선호 모드는 상위 후보에 없는 카테고리만 최대 10건씩 보충 조회하며, 실제 후보가 없는 유형은 결과 제한사항으로 알린다.

해결은 DB 데이터 변경이 아니라 후보 조회 의미, 후보 풀, 최근 기록 감쇠를 바꾸는 방식으로 적용했다.

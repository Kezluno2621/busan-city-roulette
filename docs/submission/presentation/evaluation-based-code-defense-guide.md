# City Roulette 평가 기준 기반 발표·코드 질문 대비 가이드

이 문서는 `[2026-2학기] 웹 프로그래밍 - 기말 프로젝트 평가 기준.hwp`의 항목을
City Roulette의 실제 구현과 연결한 설명서다. 발표 자료를 만들 때는 앞부분을 사용하고,
교수님이 코드에 관해 질문하면 뒷부분의 원리와 예상 질문을 참고하면 된다.

---

## 1. 프로젝트를 한 문장으로 설명하기

> City Roulette는 한국관광공사와 부산시 공공데이터를 수집·정제해 하나의 관광 장소 DB로
> 통합하고, 사용자의 출발지와 취향을 바탕으로 부산 여행 장소와 코스를 추천하는
> Spring Boot 웹 서비스입니다.

짧게 말해야 할 때는 다음과 같이 설명한다.

> 부산 여행지를 검색하고, 맞춤 추천이나 즉흥 룰렛으로 코스를 만든 뒤 회원 계정에
> 저장할 수 있는 웹 서비스입니다.

## 2. 왜 만들었는가

부산 여행을 계획하려면 장소 검색, 지도 확인, 맛집 검색, 대중교통 확인을 서로 다른
서비스에서 반복해야 한다. 선택지가 많을수록 어디를 갈지 결정하기도 어렵다.

City Roulette는 다음 문제를 해결한다.

1. 여러 공공데이터 공급자의 장소를 하나의 DB에서 검색한다.
2. 조건을 자세히 입력하고 싶으면 맞춤 코스를 만든다.
3. 결정하기 어렵다면 즉흥 룰렛으로 빠르게 코스를 만든다.
4. 마음에 든 장소와 코스를 회원 계정에 저장한다.

이 주제는 평가 기준의 **현실에서 사용할 수 있는 웹 서비스**, **기존 기술을 다른 분야에
응용한 사례**, **재미있고 편리한 주제**에 해당한다.

## 3. 평가 기준과 구현 내용 연결

## 3.1 참신성 또는 현실성 20점

### 구현한 내용

- 부산 공공 관광데이터를 실제 사용자용 검색·추천 서비스로 변환했다.
- 일반적인 추천 기능에 룰렛의 재미와 seed 재현성을 결합했다.
- 추천 결과에 점수만 보여주는 것이 아니라 추천 이유와 데이터 한계를 표시했다.
- 시간이 없거나 취향을 입력하기 싫은 사용자와 세부 조건을 입력하려는 사용자를 위해
  `즉흥 룰렛`과 `맞춤 코스 추천`을 분리했다.
- 비회원은 장소 탐색과 추천을 사용할 수 있고, 회원은 코스 저장·즐겨찾기·여행 기록을
  사용할 수 있다.

### 발표에서 할 말

> 완전히 새로운 기술을 발명한 것은 아니지만 공공데이터 수집, 추천 점수, 랜덤 추출,
> 지도와 회원 기능을 부산 즉흥 여행이라는 현실적인 문제에 결합했습니다.

## 3.2 구조 10점

프로젝트는 Spring Boot의 전형적인 3계층 구조를 사용한다.

```text
브라우저
  ↓ HTTP 요청
Controller  요청·파라미터·HTTP 응답 처리
  ↓
Service     비즈니스 규칙·추천·검증·트랜잭션
  ↓
Repository  JPA를 이용한 DB 조회·저장
  ↓
MySQL
```

도메인(Entity)은 DB 테이블과 연결된다. DTO는 외부에 필요한 데이터만 전달한다.

### 실제 예시

| 계층 | 장소 조회 | 코스 생성 | 코스 저장 |
| --- | --- | --- | --- |
| Controller | `PlaceController` | `CourseGenerationController` | `SavedCourseController` |
| Service | `PlaceService` | `CourseGenerationService` | `SavedCourseService` |
| Repository | `PlaceRepository` | `PlaceRepository` 등 | `SavedCourseRepository` |
| Domain | `Place` | `Place`, 버스 도메인 | `SavedCourse`, `SavedCoursePlace` |
| DTO | `PlaceResponse` | `CourseGenerationRequest/Response` | `SavedCourseResponse` |

### 왜 Controller에서 Repository를 바로 부르지 않았는가

Controller가 DB 규칙까지 가지면 화면 요청과 비즈니스 로직이 섞인다. Service에 규칙을
모으면 REST API와 Thymeleaf 화면에서 같은 로직을 재사용할 수 있고 단위 테스트도 쉽다.

### REST 방식

자원과 HTTP 메서드를 가능한 범위에서 일치시켰다.

| 요청 | 의미 |
| --- | --- |
| `GET /api/places` | 장소 목록 조회 |
| `GET /api/places/{id}` | 특정 장소 조회 |
| `POST /api/recommendations` | 입력 조건으로 추천 계산 |
| `POST /api/courses/generate` | 코스 결과 생성 |
| `POST /api/courses` | 생성된 코스 저장 |
| `GET /api/courses/{id}` | 저장 코스 조회 |
| `PATCH /api/courses/{id}` | 저장 코스 제목 일부 수정 |
| `DELETE /api/courses/{id}` | 저장 코스 삭제 |
| `POST /api/favorites` | 즐겨찾기 생성 |
| `DELETE /api/favorites/{placeId}` | 즐겨찾기 삭제 |

추천과 코스 생성에 POST를 사용한 이유는 입력 조건이 복잡한 JSON이고, 단순 조회 URL보다
요청 본문으로 전달하는 편이 검증과 확장에 적합하기 때문이다. 코스 생성 자체는 DB에 저장하지
않으며, 회원이 저장 버튼을 누를 때만 별도의 POST 요청으로 저장한다.

## 3.3 핵심 기능 30점

### 컨트롤러에 의한 제어

- 페이지 Controller는 Thymeleaf 화면과 Model을 반환한다.
- REST Controller는 DTO를 JSON으로 반환한다.
- `@Valid`, `@RequestParam`, `@PathVariable`로 입력을 받는다.
- 예외 처리기는 잘못된 입력, 존재하지 않는 장소, 소유권 오류 등을 적절한 HTTP 상태로
  변환한다.

### 입력과 검증

- 회원가입 폼의 아이디, 이메일, 비밀번호를 검증한다.
- 추천 요청의 위도·경도, 장소 수 1~5, 랜덤성 0~100을 검증한다.
- 반경, 페이지 크기, 검색어 길이에 상한을 둔다.
- 파일 이름과 파일 형식을 검증한다.
- 잘못된 Place ID는 404 또는 검증 오류로 처리한다.

### 보안

- Spring Security로 공개 페이지와 회원 전용 페이지를 분리한다.
- 비밀번호는 `BCryptPasswordEncoder`로 해시한다.
- CSRF 보호를 끄지 않았다. JavaScript 요청도 CSRF 토큰을 헤더에 보낸다.
- 코스와 즐겨찾기의 회원 ID를 요청 JSON에서 믿지 않고 로그인 인증정보에서 구한다.
- 다른 회원의 코스는 조회·수정·삭제할 수 없다.
- 관광 데이터 동기화 API는 관리자 권한을 요구한다.

### 예외 처리와 로그

- API HTTP 오류와 공급자 자체 오류 코드를 구분한다.
- 인증 오류는 무한 재시도하지 않는다.
- 한 원천 행의 파싱 실패가 전체 수집 실패로 번지지 않도록 건별 실패를 집계한다.
- API 키와 DB 비밀번호는 로그에 출력하지 않는다.
- `import_runs`에 수집 성공·실패·신규·갱신·건너뜀 수를 기록한다.

### DB 처리

- MySQL과 Spring Data JPA를 사용한다.
- Flyway V1~V12가 테이블과 인덱스 변경을 순서대로 재현한다.
- FK와 UNIQUE 제약조건으로 관계와 중복을 DB 차원에서도 보호한다.
- Service의 저장 로직에 `@Transactional`을 사용한다.
- 페이지네이션과 조건 검색을 DB에서 수행한다.

### HTML과 화면

- Thymeleaf로 서버 렌더링 화면을 구성했다.
- JavaScript `fetch`로 검색·추천·즐겨찾기를 처리해 필요한 영역만 갱신한다.
- Leaflet과 OpenStreetMap 타일로 장소와 코스 지도를 표시한다.
- 이미지가 없거나 라이선스가 불명확하면 대체 이미지를 사용한다.
- 모바일 360px부터 데스크톱 1440px까지 반응형 화면을 검증했다.
- 로딩, 결과 없음, 오류 상태를 별도 UI로 제공한다.

### 필수 회원 기능

| 평가 기준 | 구현 |
| --- | --- |
| 로그인 | Spring Security form login |
| 회원가입 | `MemberController`와 `MemberService`, BCrypt |
| 회원/비회원 구분 | 공개 탐색·추천과 `/my/**` 회원 기능 분리 |
| 파일 업로드 | 회원 여행 기록에 PNG 첨부 |
| 파일 다운로드 | 소유권 확인 후 첨부파일 응답 |

## 4. 추가 점수에서 가장 강한 부분

## 4.1 DB 데이터 구성 프로그램 20~30점

이 프로젝트에서 가장 강하게 강조해야 할 부분이다. 인터넷에서 받은 데이터를 그대로
복사한 것이 아니라 **수집·파싱·정규화·검증·중복 처리·저장하는 독립 프로그램**을 만들었다.

### 사용한 데이터

- 한국관광공사 TourAPI
- 부산명소정보
- 부산맛집정보
- 부산 갈맷길 관광정보
- 부산버스정보시스템 정적 버스 데이터

실제 통합 관광 장소는 4개 관광 공급자 기준 395건이다. 부산푸디투어는 개별 장소보다
테마 콘텐츠 성격이 강해 Place 저장 대상에서 제외했다. 이 판단도 데이터 정제의 일부다.

### 수집 프로그램 처리 흐름

```text
공급자 API 호출
  ↓
Raw DTO 파싱
  ↓
공급자별 Mapper
  ↓
NormalizedPlace
  ↓
필수값·좌표·레코드 유형 검증
  ↓
provider + externalId 중복 확인
  ↓
Place / PlaceSource 저장 또는 갱신
  ↓
ImportRun 통계 기록
```

### 주요 클래스

- API Client: 공급자 HTTP 요청과 JSON/XML 응답 처리
- 공급자별 PlaceMapper: 서로 다른 필드명을 공통 형식으로 변환
- `NormalizedPlace`: 공급자와 무관한 중간 데이터 형식
- `PlaceImportService`: 신규·갱신·중복 판단과 트랜잭션 저장
- `TourismImportVerificationRunner`: INSPECT, DRY_RUN, WRITE_VERIFY 안전 실행
- `PlaceDataQualityService`: 좌표·주소·이미지 누락률과 분포 분석
- `ImportRunService`: 실행 이력과 통계 보존

### 왜 Place와 PlaceSource를 분리했는가

`Place`는 서비스가 사용자에게 보여주는 대표 장소다. `PlaceSource`는 공급자, 외부 ID,
출처 URL, 라이선스, 마지막 동기화 시각을 저장한다.

한 장소가 여러 API에 등장할 수 있으므로 한 테이블에 원천 정보를 모두 넣으면 원본 추적이
어렵다. 두 테이블을 분리하면 대표 장소 하나에 여러 출처를 연결할 수 있다.

### 멱등성이란

멱등성은 같은 작업을 여러 번 실행해도 최종 결과가 같다는 뜻이다.

이 프로젝트는 `(provider, externalId)`를 원천의 유일한 키로 사용한다.

```text
처음 수집: Place + PlaceSource 생성
같은 데이터 재수집: 기존 PlaceSource를 찾고 연결된 Place 갱신
결과: 중복 행 증가 없음
```

DB의 UNIQUE 제약조건과 Service의 선조회 로직을 함께 사용해 동시 요청에서도 중복을 막는다.

### 왜 이름이 같은 장소를 자동 병합하지 않았는가

이름이 같아도 다른 지점일 수 있고 주소 표기 방식도 다르다. 잘못 병합하면 원본 복구가
어렵다. 동일 공급자와 외부 ID는 자동 갱신하지만, 다른 공급자의 유사 장소는 이름·주소·
100m 이내 좌표를 비교해 `PlaceMergeCandidate`로만 기록한다.

### Dry-run이 필요한 이유

Dry-run은 API 호출과 파싱, 정규화, 중복 판단까지 수행하지만 DB에는 쓰지 않는다.
실제 데이터 구조가 예상과 다르거나 API 오류가 있을 때 기존 DB를 보호할 수 있다.

### 발표용 핵심 문장

> 추가 점수를 위해 임의 데이터를 생성한 것이 아니라 실제 외부 API를 수집하고 공급자마다
> 다른 형식을 공통 Place 구조로 정규화하는 독립 DB 구축 프로그램을 구현했습니다.
> 같은 조건으로 재수집해도 중복이 증가하지 않도록 멱등성을 보장했습니다.

## 4.2 DB 이외의 추가 프로그램 20점

기본 CRUD를 넘어 다음 알고리즘을 별도 Service로 구현했다.

### 개인화 추천 엔진

`RecommendationScorer`가 각 후보를 0~100점으로 계산한다.

| 요소 | 기본 가중치 | 의미 |
| --- | ---: | --- |
| 선호 카테고리 | 30 | 사용자가 선택한 유형과 일치하는가 |
| 직선거리 | 30 | 출발지에서 가까운가 |
| 다양성 | 15 | 후보에서 너무 흔한 유형만 반복하지 않는가 |
| 데이터 품질 | 15 | 주소·설명·이미지가 충실한가 |
| 교통 연결성 | 10 | 현재 적재 데이터에서 검증 가능한가 |

가중 평균식은 다음과 같다.

```text
총점 = Σ(요소 점수 × 가중치) / 실제로 평가한 가중치의 합
```

교통 데이터를 평가할 수 없으면 교통 점수를 0점으로 벌점 처리하지 않는다. 교통 가중치
자체를 분모와 분자에서 제외하고 나머지 점수를 다시 정규화한다. 데이터가 부족하다는 이유로
장소를 이동 불가능하다고 판단하지 않기 위해서다.

거리 점수는 최대 거리 50km 안에서 가까울수록 높아진다. 실제 도로 거리가 아니라
Haversine 공식으로 구한 두 위·경도 사이의 직선거리다.

### 룰렛 선택

- 점수가 높은 장소의 선택 확률을 높이는 가중 추출을 사용한다.
- 한 번 선택한 장소를 후보에서 제거하는 비복원 추출로 중복 선택을 막는다.
- `randomness=0`이면 높은 점수 순으로 결정론적으로 선택한다.
- 랜덤성이 높아지면 후보 선택 범위가 넓어진다.
- 같은 `randomSeed`와 후보 목록이면 같은 결과를 재현한다.
- 일반 실행은 매번 새로운 seed를 사용한다.
- 최근 즉흥 룰렛 결과를 브라우저에 기록해 반복을 줄인다.

### 코스 다양성과 방문 순서

- 장소를 음식, 카페, 관광, 문화, 산책 등의 역할로 분류한다.
- 아직 선택하지 않은 역할에 다양성 보너스를 준다.
- 음식점이 연속되는 순서에 불이익을 준다.
- 최대 5개 장소이므로 가능한 순열을 최대 120개 비교할 수 있다.
- 거리 제한 안에서 역할 반복이 적고 직선거리 합이 짧은 순서를 선택한다.
- 이를 실제 도로 최단 경로나 실제 소요시간이라고 주장하지 않는다.

### 버스 경로 탐색

- `BusRoute → BusRouteStop → BusStop` 관계를 방향과 정차 순서를 가진 그래프로 본다.
- 출발 정류장 순번이 도착 정류장보다 앞선 경우만 직통 후보로 인정한다.
- 한 번 환승은 두 노선이 동일한 공식 정류장 ID를 공유할 때 탐색한다.
- 반대 방향이나 정차 순서가 끊긴 구간은 확정 경로로 반환하지 않는다.
- 현재 버스 데이터가 부분적이므로 `NO_CANDIDATE`는 부산 전체에서 경로가 없다는 뜻이 아니다.

### 발표용 핵심 문장

> DB 검색 결과를 그대로 보여주는 데서 끝나지 않고 추천 점수 계산, seed 기반 가중 추출,
> 카테고리 다양성 보정과 방문 순서 결정을 별도 알고리즘으로 구현했습니다.

## 4.3 상업적 또는 학술적 가치 5점

### 상업적 가치

- 부산 관광 플랫폼, 지역 행사, 숙박 서비스와 연결할 수 있다.
- 지역별 장소 노출과 추천으로 덜 알려진 장소의 방문을 유도할 수 있다.
- 즐겨찾기와 저장 코스는 향후 사용자 행동 분석의 기반이 된다.

### 학술적 가치

- 서로 다른 공공데이터 스키마를 하나의 모델로 정규화했다.
- 출처와 라이선스를 별도 관리하는 데이터 계보 구조를 사용했다.
- 불완전한 교통 데이터에서 결과를 과장하지 않는 불확실성 처리 방식을 적용했다.
- 고정 seed로 랜덤 알고리즘의 테스트 재현성을 확보했다.

## 5. 핵심 기능별 코드 흐름

## 5.1 관광지 목록 조회

```text
GET /places?district=해운대구&category=CAFE&page=0
  ↓
PlaceExplorerController
  ↓
PlaceExplorerService / PlaceService
  ↓
PlaceRepository
  ↓
Page DTO를 Model에 저장
  ↓
places/list.html 렌더링
```

전체 장소를 Java 메모리로 읽지 않고 DB에서 필터와 페이지네이션을 수행한다.

## 5.2 추천 요청

```text
POST /api/recommendations
  ↓ JSON + @Valid
PersonalizedRecommendationController
  ↓
PersonalizedRecommendationService
  ↓
RecommendationCandidateFilter  DB 후보 제한
  ↓
RecommendationScorer          요소별 점수 계산
  ↓
상위 후보만 교통 평가
  ↓
RecommendationResultDto JSON 반환
```

Entity를 JSON으로 직접 노출하지 않아 JPA 지연 로딩 문제와 내부 필드 노출을 피한다.

## 5.3 코스 생성과 저장

```text
POST /api/courses/generate
  ↓
CourseGenerationService
  ↓ 추천 후보 선택·방문 순서 계산
GeneratedCourseRegistry가 일회성 저장 토큰 발급
  ↓
브라우저가 코스 표시
  ↓ 사용자가 저장 선택
POST /api/courses + 저장 토큰
  ↓
SavedCourseService가 토큰 소비·회원 확인·스냅샷 저장
```

생성 API가 DB에 자동 저장하지 않는 이유는 비회원도 추천을 사용할 수 있고, 사용자가
명시적으로 저장한 결과만 회원 데이터로 남기기 위해서다.

일회성 토큰은 클라이언트가 추천 결과의 점수나 장소 목록을 조작해서 저장하는 것을 막는다.
서버가 생성해 보관한 스냅샷을 토큰으로 찾아 저장한다.

## 5.4 즐겨찾기

```text
POST /api/favorites {placeId}
  ↓
인증정보에서 현재 회원 확인
  ↓
Place 존재 여부 확인
  ↓
PlaceFavorite 저장
```

`UNIQUE(member_id, place_id)`가 같은 장소의 중복 즐겨찾기를 막는다.

## 5.5 파일 업로드와 다운로드

- 업로드할 때 파일명, 확장자, MIME 형식과 크기를 검증한다.
- 서버 저장명은 원본 파일명과 분리해 충돌과 경로 조작을 막는다.
- 다운로드할 때 여행 기록 소유자를 확인한다.
- DB에는 파일 메타데이터를, 디스크에는 실제 파일을 저장한다.

## 6. 교수님이 물어볼 가능성이 높은 질문과 답변

### Q1. 이 프로젝트에서 가장 핵심적인 기능은 무엇인가요?

공공데이터를 수집해 통합 장소 DB를 만드는 프로그램과, 그 데이터를 사용하는 추천·룰렛
엔진이다. 회원 CRUD만 구현한 것이 아니라 데이터 생성부터 사용자 결과까지 연결했다.

### Q2. 3계층 구조를 어디에서 확인할 수 있나요?

예를 들어 코스 생성은 `CourseGenerationController`가 요청을 받고,
`CourseGenerationService`가 추천과 순서를 계산하며, `PlaceRepository`가 장소를 조회한다.
Entity와 DTO도 분리되어 있다.

### Q3. DTO를 사용하는 이유는 무엇인가요?

Entity는 DB 구조와 관계를 포함한다. 이를 직접 반환하면 비밀번호 같은 내부 정보가 노출될
수 있고 지연 로딩과 순환 참조 문제가 생길 수 있다. DTO는 API에 필요한 값만 명시한다.

### Q4. `@Transactional`은 왜 사용하나요?

여러 INSERT와 UPDATE를 하나의 작업으로 묶기 위해서다. 중간에 오류가 발생하면 전부
롤백해 일부만 저장되는 상태를 막는다. 조회 메서드는 `readOnly=true`로 의도를 표시한다.

### Q5. JPA와 Flyway의 역할 차이는 무엇인가요?

JPA는 Java 객체와 DB 행을 연결하고 조회·저장을 돕는다. Flyway는 V1부터 V12까지 SQL을
순서대로 실행해 어느 환경에서도 같은 스키마를 만들게 한다.

### Q6. 중복 데이터는 어떻게 막나요?

Service에서 `provider + externalId`로 기존 PlaceSource를 먼저 찾고, DB에도 같은 조합의
UNIQUE 제약조건을 둔다. 애플리케이션과 DB 두 단계로 보호한다.

### Q7. 왜 장소 이름으로 중복을 판단하지 않았나요?

같은 이름의 다른 지점이 존재할 수 있기 때문이다. 이름과 주소, 좌표가 비슷한 데이터는
자동 병합하지 않고 검토 후보로만 저장한다.

### Q8. 추천 점수 90점은 만족도 90%라는 뜻인가요?

아니다. 카테고리, 거리, 다양성, 데이터 품질을 비교하기 위한 정규화 점수다. 실제 사용자
만족도나 이동시간을 예측한 값은 아니다.

### Q9. 교통 데이터가 없으면 왜 0점을 주지 않나요?

0점은 연결이 나쁘다는 뜻인데 현재는 데이터가 부족해 모르는 상태다. 그래서 교통 가중치를
제외하고 나머지 요소로 다시 계산해 알 수 없음과 나쁨을 구분한다.

### Q10. Haversine 공식은 무엇인가요?

지구를 구로 보고 두 위·경도 사이의 대권 직선거리를 계산하는 공식이다. 빠르게 거리 후보를
비교할 수 있지만 실제 도로·도보 거리는 아니다.

### Q11. 랜덤 결과를 어떻게 테스트하나요?

`SplittableRandom`에 고정 seed를 전달한다. 입력 후보와 seed가 같으면 같은 선택 순서가
나오므로 테스트에서 결과를 재현할 수 있다.

### Q12. 룰렛 애니메이션이 장소를 선택하나요?

아니다. 서버가 먼저 최종 장소를 결정한다. JavaScript 룰렛은 서버 결과를 순서대로 보여주는
시각 효과다. 애니메이션 결과와 저장되는 결과가 달라지는 문제를 막았다.

### Q13. 출발지를 선택하지 않은 즉흥 룰렛은 어떻게 동작하나요?

후보 거리 계산에는 부산 중심 기준점을 내부적으로 사용하지만 실제 출발지로 표시하지 않는다.
API는 `selectedByUser=false`를 반환하고 지도는 1번 추천 장소부터 그린다.

### Q14. 최대 5곳인데 왜 순열을 비교할 수 있나요?

5개의 전체 순열은 `5! = 120`개다. 현재 범위에서는 충분히 작은 수라 각 순서의 역할 반복과
거리 합을 비교할 수 있다. 장소 수가 커지면 같은 방식은 비효율적이므로 다른 최적화가 필요하다.

### Q15. CSRF는 무엇이고 어떻게 처리했나요?

로그인된 사용자의 브라우저를 악용해 원하지 않는 변경 요청을 보내는 공격이다. Spring
Security의 기본 CSRF 보호를 유지하고, JavaScript POST·PATCH·DELETE 요청은 페이지의
CSRF 토큰을 헤더에 넣는다.

### Q16. 비밀번호는 DB에 어떻게 저장되나요?

원문이 아니라 BCrypt 해시로 저장한다. BCrypt는 같은 비밀번호도 salt 때문에 다른 해시가
될 수 있고 로그인할 때 해시 비교를 수행한다.

### Q17. 다른 회원의 코스를 어떻게 막나요?

코스 ID만 조회하지 않고 `코스 ID + 현재 로그인 회원` 조건으로 조회한다. 요청자가 회원 ID를
보내도록 하지 않는다.

### Q18. 오래된 화면에서 코스를 수정하면 어떻게 되나요?

SavedCourse의 version 값을 비교하는 낙관적 잠금을 사용한다. 다른 요청이 먼저 변경했다면
HTTP 409 Conflict를 반환해 최신 데이터를 덮어쓰지 않는다.

### Q19. 서버 시작 시 데이터를 자동 수집하지 않은 이유는 무엇인가요?

API 호출량과 DB 변경을 통제하기 위해서다. 수집은 명시적인 Runner 모드로만 실행하고
DRY_RUN과 안전 확인을 거쳐야 한다.

### Q20. 버스 경로 탐색의 한계는 무엇인가요?

실제 검증 데이터는 부산 100번 노선 일부 구간이다. 따라서 경로 후보가 없다는 결과는 부산
전체에서 이동할 수 없다는 뜻이 아니다. 실시간 도착시간과 실제 소요시간도 계산하지 않는다.

### Q21. 왜 MySQL 인덱스를 사용했나요?

장소 검색과 주변 정류장 후보 조회 시 전체 행을 매번 읽지 않기 위해서다. 정류장은 위도·경도
bounding box로 먼저 줄인 뒤 Haversine 거리를 계산한다.

### Q22. 테스트는 무엇을 검증하나요?

파싱과 정규화 단위 테스트, Service 비즈니스 규칙, Controller 상태코드와 보안, H2 Fixture
추천·경로 시나리오, MySQL 마이그레이션·멱등성, 실제 Chromium 사용자 흐름을 구분해 검증했다.

## 8. 시연 순서

1. 관광지 목록에서 구·군 또는 카테고리를 검색한다.
2. 장소 상세에서 지도와 출처를 보여준다.
3. 즉흥 룰렛으로 3곳을 뽑고 방문 순서와 지도 결과를 보여준다.
4. 맞춤 코스에서 출발지와 음식점 선호를 선택해 혼합 코스를 보여준다.
5. 로그인 후 코스를 저장한다.
6. 내 코스 상세와 즐겨찾기를 보여준다.

시연 시간이 부족하면 회원가입과 파일 업로드는 화면만 보여주고 “필수 기능으로 구현했으며
자동화 테스트와 브라우저에서 검증했다”고 설명한다.

- “같은 이름의 장소는 자동으로 하나로 합칩니다.”

대신 다음처럼 말한다.

- “현재 적재된 정적 버스 데이터 범위에서 후보를 찾습니다.”
- “Haversine 직선거리를 이용한 방문 순서 휴리스틱입니다.”
- “검증할 데이터가 없는 시간과 비용은 UNKNOWN으로 표시합니다.”
- “설명 가능한 가중치 기반 추천 알고리즘입니다.”

## 10. 마지막에 기억할 다섯 문장

1. **웹 구조:** Controller는 요청, Service는 규칙, Repository는 DB를 담당합니다.
2. **DB 추가 점수:** 외부 API를 정규화하고 멱등 저장하는 독립 수집 프로그램을 만들었습니다.
3. **알고리즘 추가 점수:** 추천 점수, seed 기반 가중 추출과 코스 다양성 알고리즘을 구현했습니다.
4. **보안:** 인증정보에서 회원을 확인하고 CSRF, BCrypt, 소유권 검증을 적용했습니다.
5. **정직한 한계:** 없는 시간·비용·교통 정보를 임의로 만들지 않고 데이터 한계를 표시합니다.

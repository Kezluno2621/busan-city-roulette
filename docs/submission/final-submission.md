# City Roulette 웹 프로그래밍 기말 프로젝트

## 1. 프로젝트 기본 정보

- **프로젝트명:** City Roulette
- **주제:** 부산 대중교통 기반 즉흥 여행 추천 서비스
- **개발 환경:** Java 17, Spring Boot 3.5.16, Gradle 8.14.3, MySQL 8, Thymeleaf, JavaScript, CSS, Leaflet
- **개발 목적:** 사용자가 여행 목적지를 미리 정하지 않아도 출발 위치와 선호 조건을 기준으로 방문 후보와 코스를 추천받을 수 있는 웹 서비스를 구현한다.

City Roulette는 전체 장소 중 하나를 무작위로 고르는 프로그램이 아니다. 먼저 DB에서 조건에 맞는 후보를 조회하고 각 후보를 점수화한 다음, 사용자가 지정한 랜덤성 범위 안에서 가중 랜덤을 적용한다.

## 2. 개발 배경 및 목적

부산 여행을 준비할 때 사용자는 목적지를 직접 정하고 관광지, 지도, 대중교통 정보를 여러 서비스에서 따로 찾아야 한다. 이 과정에서는 익숙한 장소만 반복해서 선택하기 쉽고, 짧은 시간에 즉흥적인 코스를 만들기 어렵다.

City Roulette는 다음 문제를 해결하는 것을 목표로 한다.

- 목적지를 직접 결정해야 하는 부담을 줄인다.
- 부산 관광 공공데이터를 자체 DB로 통합해 한 화면에서 탐색한다.
- 출발지, 선호 카테고리, 지역, 랜덤성을 함께 고려한다.
- 높은 점수의 장소만 반복하는 문제를 가중 랜덤과 카테고리 다양성으로 완화한다.
- 검증할 수 없는 시간·비용·교통 정보는 임의로 생성하지 않고 한계로 표시한다.

## 3. 핵심 기능

### 3.1 여행지 탐색

비회원도 `/places`에서 장소명, 카테고리, 부산 구·군을 함께 검색할 수 있다. 결과는 서버 측 페이지네이션으로 조회하며 상세 화면에서 주소, 설명, 이미지, 데이터 출처, 지도와 주변 정류장을 확인한다.

### 3.2 여행 추천과 룰렛 코스

- **즉흥 룰렛:** 조건 입력을 최소화하고 1~5개 장소를 빠르게 선택한다.
- **맞춤 코스:** 출발지, 지역, 선호 카테고리, 장소 수와 랜덤성을 반영한다.
- 동일한 장소는 한 코스에 중복 선택하지 않는다.
- 사용자가 명시한 `randomSeed`와 후보 집합이 같으면 결과를 재현할 수 있다.
- 방문 순서는 음식점 연속과 동일 역할 연속을 줄이고 직선 이동거리도 함께 고려한다.

### 3.3 관광지 DB

한국관광공사와 부산 공공데이터의 서로 다른 응답을 공급자 DTO와 Mapper로 변환한 뒤 `Place`와 `PlaceSource`로 저장한다. 화면이 외부 API 응답에 직접 의존하지 않으므로 검색, 추천, 코스 생성은 저장된 장소 데이터만으로도 실행할 수 있다.

### 3.4 회원 기능

- 회원가입, 로그인, 로그아웃
- Spring Security Session 인증
- 회원·비회원 접근 제어와 CSRF 보호
- 회원별 즐겨찾기, 저장 코스, 여행 기록 분리

### 3.5 코스 저장

로그인 회원은 서버가 생성한 일회성 코스 토큰으로 코스를 저장한다. 저장된 코스는 생성 당시 장소명, 방문 순서, 추천 점수와 이유를 스냅샷으로 보존하며 목록·상세·제목 수정·삭제를 지원한다. 소유자가 아닌 회원의 조회와 변경은 차단한다.

### 3.6 여행 기록

회원은 방문 장소, 방문일, 메모와 선택적 이미지를 여행 기록으로 남길 수 있다. 목록과 상세 조회는 로그인한 본인의 데이터로 제한한다.

### 3.7 즐겨찾기

로그인 회원은 관광 장소를 즐겨찾기에 추가·해제하고 `/my/favorites`에서 다시 확인할 수 있다. `(member_id, place_id)` 유일 제약으로 중복 저장을 방지한다.

### 3.8 지도와 교통 정보

Leaflet과 OpenStreetMap 타일로 장소와 정류장 좌표를 표시한다. 자체 부산버스 정적 데이터에서는 직통 및 최대 1회 환승 후보를 찾으며, ODsay는 별도의 외부 좌표 기반 대중교통 조회 기능으로 분리되어 있다.

## 4. 관광지 데이터 구축

### 4.1 처리 흐름

```text
공공데이터 API
↓
JSON 또는 XML 응답
↓
공급자별 DTO
↓
공급자별 Mapper
↓
NormalizedPlace
↓
검증·정규화·중복 후보 탐색
↓
Place + PlaceSource
↓
MySQL
```

외부 API 결과를 화면에 바로 표시하지 않고 서비스 내부 형식으로 정제해 자체 DB를 구축한다. 수집 Runner는 기본적으로 비활성화되어 있으며, 명시적으로 모드를 선택했을 때만 실행된다.

### 4.2 TourAPI 대표 매핑

| TourAPI 필드 | 내부 필드 |
|---|---|
| `contentid` | `PlaceSource.externalId` |
| `title` | `Place.name` |
| `addr1`, `addr2` | 정규화된 `Place.address` |
| `mapx` | WGS84 경도 |
| `mapy` | WGS84 위도 |
| `contenttypeid` | 통합 카테고리 |
| `firstimage` | 라이선스 확인 후 대표 이미지 |
| `modifiedtime` | 원천 수정 시각 |

`PlaceSource`에는 공급자, 외부 ID, 원본 URL, 원천 카테고리, 수정·동기화 시각, 출처와 라이선스를 보존한다.

### 4.3 중복과 멱등성

- 동일 `(provider, externalId)`는 새 장소를 만들지 않고 기존 원천과 장소를 갱신한다.
- 한 번의 응답 안에서 같은 외부 ID가 반복되면 건너뛴다.
- 다른 공급자의 장소는 이름만 같다는 이유로 자동 병합하지 않는다.
- 정규화된 이름과 주소가 같거나 같은 이름이면서 좌표가 100m 이내이면 `PlaceMergeCandidate`로 기록해 검토 대상으로 남긴다.
- 이미지 라이선스가 비어 있으면 이미지 URL을 대표 이미지로 저장하지 않는다.
- `ImportRun`으로 공급자별 실행 결과와 실패 통계를 기록한다.

검증된 demo 데이터 스냅샷은 Place 395건, PlaceSource 395건이며 TourAPI, 부산명소, 부산맛집, 부산갈맷길 네 공급자가 포함되어 있다. 부산푸디투어 표본은 개별 장소가 아닌 테마 콘텐츠여서 Place 적재 대상에서 제외했다.

## 5. 추천 알고리즘

### 5.1 전체 흐름

```text
1. PlaceRepository에서 최대 200개의 후보 조회
2. 좌표, 지역, 카테고리 조건 검증
3. 출발지와 각 장소의 Haversine 직선거리 계산
4. 카테고리·거리·다양성·데이터 품질 점수 계산
5. 상위 후보 일부의 자체 정적 버스 경로 검증
6. 총점 내림차순 정렬
7. randomness 값에 따라 선택 후보 pool 확대
8. 추천 점수 기반 weighted random 비복원 추출
9. 역할 다양성과 직선거리를 고려해 방문 순서 결정
```

모든 후보에 외부 교통 API를 호출하지 않는다. DB 필터와 후보 수 상한을 먼저 적용하고, 교통 평가는 설정된 상위 후보에 한정한다.

### 5.2 추천 점수

각 항목을 0~100으로 만든 뒤 설정 가중치로 평균한다.

| 점수 요소 | 기본 가중치 | 의미 |
|---|---:|---|
| 카테고리 | 30 | 선택한 선호 카테고리와 일치하는지 평가 |
| 거리 | 30 | 50km 상한 안에서 출발지와 가까울수록 높은 점수 |
| 다양성 | 15 | 후보 집합에서 과도하게 많은 카테고리의 점수를 조정 |
| 데이터 품질 | 15 | 기본 60점에 주소 20점, 설명 10점, 표시 가능한 이미지 10점 추가 |
| 교통 | 10 | 자체 정적 버스 데이터에서 검증된 경우에만 포함 |

교통을 검증하지 못했거나 데이터가 부분 적재 상태이면 교통 항목을 0점으로 벌점 처리하지 않는다. 교통 가중치를 분모에서 제외하고 나머지 점수만 재정규화한다.

### 5.3 Weighted Random과 seed

- `randomness = 0`: 점수, 거리, ID 순으로 정렬된 상위 후보를 결정론적으로 선택한다.
- 랜덤성이 증가하면 상위 결과 수를 넘어 선택 가능한 후보 pool이 넓어진다.
- 개인화 추천의 가중 추출은 `score + 1`을 사용해 점수가 높은 후보의 선택 확률을 높이면서 0점 후보도 선택 가능성을 유지한다.
- 코스 선택은 랜덤성에 따라 점수 가중치 지수를 완화하고, 아직 선택되지 않은 장소 역할에 다양성 가중치를 추가한다.
- 추출한 장소는 pool에서 제거해 같은 코스 안의 중복을 방지한다.
- 명시적인 seed가 없으면 요청마다 새 seed를 만들고, 같은 seed와 같은 후보 집합이면 결과를 재현한다.

### 5.4 방문 순서

먼저 nearest-neighbor 방식으로 직선거리 기준 순서를 만든다. 장소가 최대 5개이므로 가능한 순열을 비교하고, 기준 순서 거리의 `1.35배 + 1km` 범위 안에서 다음 순으로 더 나은 코스를 고른다.

1. 음식점 연속 방문이 적은 순서
2. 동일 역할 연속 방문이 적은 순서
3. 총 직선거리가 짧은 순서

이는 실제 도로 최단 경로나 실제 이동시간 최적화가 아니다.

## 6. 거리 계산

`DistanceCalculator`는 지구 반지름 6,371km와 Haversine 공식을 사용해 두 위도·경도 사이의 대권 **직선거리**를 계산한다. 좌표 오차를 고려해 중간값을 0~1로 제한한 뒤 km와 m 단위로 변환한다.

Haversine은 DB 후보의 대략적인 근접도와 주변 정류장 범위를 빠르게 계산하는 데 사용한다. 계산 결과는 실제 도보 거리, 도로 거리나 버스 운행거리로 표현하지 않는다.

## 7. 교통 정보

### 자체 부산버스 정적 데이터

- `BusStop`, `BusRoute`, `BusRouteStop`을 MySQL에 저장한다.
- 공식 정류장 ID와 노선 외부 ID로 중복을 방지한다.
- 정차 순서와 방향을 보존한 그래프로 직통 및 최대 1회 환승 후보를 찾는다.
- 추천 엔진의 교통 점수는 이 자체 정적 데이터에서 `VERIFIED`인 경우에만 포함한다.

현재 검증된 demo 스냅샷은 정류장 30건, 노선 1건, 정차 관계 20건의 부분 데이터다. 후보가 없더라도 부산 전체에서 이동할 수 없다고 판단하지 않고 `PARTIAL_DATA` 또는 `UNVERIFIED`로 표시한다.

### ODsay

`OdsayApiClient`는 출발·도착 좌표를 이용하는 외부 대중교통 경로 조회에 사용한다. 자체 버스 그래프와 응답 DTO를 분리했으며, 키 누락이나 외부 오류가 추천 DB 기능 전체를 중단시키지 않도록 오류를 변환해 안내한다. ODsay 결과는 현재 추천 점수의 자체 버스 검증과 동일한 데이터로 취급하지 않는다.

## 8. 시스템 구조

```text
Browser
↓
Spring Security
↓
Controller  ─ HTTP 요청, Validation, View/JSON 응답
↓
Service     ─ 추천·코스·회원·수집 등 비즈니스 로직
├─ TourismApiClient / 부산 공공데이터 Client
├─ KakaoLocalApiClient
└─ OdsayApiClient
↓
Repository  ─ Spring Data JPA 기반 DB 접근
↓
MySQL
```

- **Entity:** DB 테이블과 관계를 표현한다.
- **DTO:** Entity 직접 노출을 막고 화면·REST·외부 API 계약을 분리한다.
- **Mapper:** 외부 공급자 필드를 내부 정규화 구조로 변환한다.
- **Runner:** 웹 요청과 분리된 수동 수집·검증 진입점이다.

패키지별 상세 역할은 [`package-structure.md`](../architecture/package-structure.md)에 정리되어 있다.

## 9. 회원 인증

- Spring Security의 Session 기반 폼 로그인을 사용한다.
- 비밀번호는 `BCryptPasswordEncoder`로 해시한 뒤 저장한다.
- 회원가입 시 아이디·이메일 중복을 서비스와 DB 유일 제약으로 함께 처리한다.
- 공개 기능: 메인, 관광지 탐색·상세, 추천·룰렛 생성, 지도, 공개 REST 조회.
- 회원 기능: `/my/**`, 코스 저장·수정·삭제, 즐겨찾기, 여행 기록과 첨부 다운로드.
- 관광 데이터 동기화와 개발 진단 API는 관리자 권한을 요구한다.
- CSRF 보호를 비활성화하지 않았다.

## 10. 파일 처리

```text
MultipartFile
↓
크기·Content-Type·확장자·파일명 검증
↓
FileStorageService
↓
UUID 기반 저장명으로 서버 파일 저장

원본명·저장명·형식·크기
↓
TripRecord
↓
MySQL
```

- 파일 크기는 5MB 이하로 제한한다.
- JPG, PNG, WEBP만 허용하며 Content-Type과 확장자가 일치해야 한다.
- 사용자 파일명을 서버 저장명으로 사용하지 않고 UUID를 사용한다.
- `..`, 경로 구분자와 허용되지 않은 저장 파일명으로 발생할 수 있는 경로 이탈을 차단한다.
- DB 저장이 실패하면 먼저 저장한 파일을 정리한다.
- 다운로드 전에 `TripRecordService`가 로그인 회원과 기록 소유권을 함께 조회한다.

## 11. 주요 데이터 모델

| Entity | 역할 |
|---|---|
| `Member` | 로그인 계정, BCrypt 비밀번호와 역할을 저장한다. |
| `Place` | 검색과 추천에 사용하는 정규화된 대표 장소다. |
| `PlaceSource` | 장소의 공급자, 외부 ID, 출처와 라이선스를 보존한다. |
| `PlaceMergeCandidate` | 공급자가 다른 유사 장소를 자동 병합하지 않고 검토 대상으로 기록한다. |
| `ImportRun` | 공공데이터 수집 실행 상태와 통계를 저장한다. |
| `BusStop`, `BusRoute`, `BusRouteStop` | 정류장·노선·정차 순서를 포함한 정적 교통 그래프를 구성한다. |
| `SavedCourse` | 회원이 저장한 코스의 출발지, 조건, 한계와 version을 보존한다. |
| `SavedCoursePlace` | 저장 당시 방문 순서, 장소 정보와 추천 근거의 스냅샷이다. |
| `PlaceFavorite` | 회원과 장소의 즐겨찾기 관계다. |
| `TripRecord` | 회원의 방문일, 메모와 선택적 첨부 파일 메타데이터다. |

## 15. 예외 및 Validation

- Jakarta Validation으로 회원가입, 추천, 코스, 페이지 크기와 여행 기록 입력을 제한한다.
- 출발지 ID와 좌표의 동시 입력, 좌표 누락과 범위를 서비스에서 검사한다.
- 회원가입 아이디·이메일 중복과 DB 동시 요청 충돌을 사용자 오류로 변환한다.
- 존재하지 않는 장소·버스·코스는 적절한 404 응답 또는 오류 화면으로 처리한다.
- 저장 코스의 오래된 version 수정은 충돌 응답으로 처리한다.
- 외부 API는 HTTP 오류, 인증 오류, 공급자 결과 코드와 파싱 오류를 구분한다.
- 파일 크기·형식·저장 실패는 폼 오류 또는 안전한 서버 오류로 변환한다.
- 예외 응답에서 API 키, DB 비밀번호와 상세 스택 트레이스를 노출하지 않는다.

## 16. 개발 중 주요 문제와 해결

### 외부 API 형식과 내부 DB의 차이

공급자마다 이름, 주소, 좌표, 카테고리와 중첩 응답 구조가 달랐다. 공급자별 DTO와 Mapper를 두고 `NormalizedPlace`를 거쳐 `Place`와 `PlaceSource`로 저장해 화면과 외부 API 계약을 분리했다.

### 재수집 중복과 공급자 간 유사 장소

동일 공급자의 재수집은 `(provider, externalId)`로 갱신해 멱등성을 보장했다. 공급자가 다른 유사 장소는 잘못 합쳐질 위험이 있어 자동 병합하지 않고 `PlaceMergeCandidate`로 기록했다.

### 추천 결과의 반복과 한 카테고리 편중

점수 순으로만 반환하면 같은 장소와 같은 유형이 반복됐다. 점수 기반 weighted random, seed 재현, 비복원 추출, 역할 그룹 다양성 및 음식점 연속 최소화를 적용했다.

### 교통 데이터 부족과 외부 호출 부담

모든 후보에 교통 경로를 계산하지 않고 DB와 거리로 후보를 제한한 뒤 상위 일부만 자체 정적 그래프로 평가했다. 데이터가 부분 적재 상태이면 추천을 제거하지 않고 검증 수준을 결과에 표시했다.

## 17. 현재 한계

- Haversine 결과는 실제 도보·도로·버스 이동거리가 아닌 직선거리다.
- 자체 부산버스 데이터는 부산 100번 노선의 검증된 일부 구간이므로 부산 전체 접근성을 대표하지 않는다.
- 실제 방문 체류시간, 영업시간, 입장료와 교통요금 데이터가 없어 시간·예산을 정확히 평가하지 않는다.
- 실제 버스 운행 형상, 실시간 도착정보와 다중 환승 최적화는 지원하지 않는다.
- ODsay와 Kakao 기능은 유효한 키와 인터넷 연결이 필요하다.
- Leaflet 지도 라이브러리와 OpenStreetMap 타일은 오프라인에서 완전하게 표시되지 않을 수 있다.
- 공개 배포 대신 검증된 로컬 demo 환경을 사용한다.

## 18. 향후 발전 방향

- 부산 전체 버스 정적 노선망을 검증된 초기 적재 자료로 확장
- 실시간 도착정보의 짧은 TTL 캐시와 사용자 요청 시 조회
- 영업시간, 입장료, 평균 체류시간을 제공하는 검증된 데이터 연계
- 날씨와 실내·실외 특성을 반영한 추천
- 실제 도보·대중교통 이동시간을 이용한 하루 일정 최적화
- 모바일 UX 고도화와 안전한 공개 배포 환경 구축

# Phase 3-B 사용자 조건 기반 장소 추천 엔진

## 구현 범위

Phase 3-B는 한 번의 요청에서 개별 장소 후보를 추천한다. 여러 장소를 순서대로 연결하는 코스 생성은 포함하지 않는다. 기존 ODsay 기반 `GET /api/recommendations/random`은 그대로 유지하고, 새 기능은 `POST /api/recommendations`로 분리했다.

처리 흐름은 다음과 같다.

`RecommendationRequest` → DB 후보 필터 → 중복 장소명 제거 → 기본 점수 계산 → 상위 후보만 정적 버스 경로 평가 → 점수 재정규화 → 확률 기반 후보 선택 → DTO 반환

## 후보 조회와 안전 제한

- 좌표가 있고 `merge_status`가 `ACTIVE`(또는 기존 NULL)인 장소만 조회한다.
- 카테고리와 구·군 조건은 JPA 쿼리에서 먼저 적용한다.
- 후보 풀은 기본 최대 200건이며 요청 수의 10배, 최소 50건 범위에서 제한한다.
- `normalized_name` 또는 공백을 제거한 장소명으로 한 요청 안의 중복을 제거한다.
- 출발 장소 ID를 사용하면 해당 장소는 후보에서 제외한다.
- 원본/격리 MySQL에 쓰지 않으며 이 기능은 읽기 전용 트랜잭션이다.

## 점수 계산

각 요소는 0~100으로 정규화하고 아래 기본 가중치를 적용한다.

| 요소 | 가중치 | 기준 |
|---|---:|---|
| 선호 카테고리 | 30 | 요청 카테고리 일치 여부. 선호 미지정 시 중립 100 |
| 직선거리 | 30 | 0~50km를 100~0으로 선형 정규화 |
| 다양성 | 15 | 후보 풀에서 상대적으로 적은 카테고리에 높은 점수 |
| 데이터 품질 | 15 | 이름·카테고리·좌표를 기본으로 주소·설명·이미지 보유 여부 |
| 교통 연결성 | 10 | 현재 적재된 연속 정차 구간에서 `VERIFIED`인 경우에만 포함 |

설정은 `recommendation.weights.*` 속성으로 조정한다. 교통을 검증하지 못했거나 부분 데이터인 후보는 0점 감점을 주지 않고 교통 가중치 자체를 분모와 분자에서 제외해 재정규화한다.

`distanceMeters`는 Haversine 직선거리이며 도보 경로나 실제 이동거리가 아니다. 실제 이동시간, 방문시간, 입장료, 교통요금 데이터는 생성하거나 추정하지 않는다.

## 랜덤성

랜덤성은 계산된 점수를 변경하지 않는다. 점수순 상위 풀의 크기를 `randomness` 0~100에 따라 넓힌 뒤 `(score + 1)`을 가중치로 비복원 추출한다. `randomSeed`를 전달하면 같은 데이터와 요청에서 선택 순서를 재현할 수 있다.

## 교통 엔진 연동

- Place ID 출발지일 때만 `TransitRoutePlannerService`를 호출한다.
- 점수 상위 후보 중 최대 10건만 평가하고 후보별 최대 경로 1건을 요청한다.
- 검증된 경로 후보가 있을 때만 `VERIFIED` 및 교통 점수를 적용한다.
- 부분 적재 상태에서 후보가 없으면 `PARTIAL_DATA`로 반환하고 추천에서는 제거하지 않는다.
- 좌표 출발지는 정적 경로 엔진이 Place ID를 요구하므로 `NOT_EVALUATED`로 반환한다.
- 현재 부산 100번 노선 일부만 검증된 상태이므로 `NO_CANDIDATE`를 부산 전체에서 이동 불가능하다는 뜻으로 해석하지 않는다.

## REST API

### 요청

```http
POST /api/recommendations
Content-Type: application/json
```

```json
{
  "originPlaceId": 1,
  "categories": ["ATTRACTION", "CAFE"],
  "district": "해운대구",
  "availableMinutes": 180,
  "budget": 30000,
  "randomness": 50,
  "limit": 10,
  "randomSeed": 42
}
```

`originPlaceId` 대신 `originLatitude`와 `originLongitude`를 함께 사용할 수 있다. ID와 좌표를 동시에 전달하거나 좌표 한쪽만 전달하면 400이다. 위·경도 범위, 양수 시간, 음수 아닌 예산, `randomness` 0~100, `limit` 1~20을 검증한다. 없는 Place ID는 404, 좌표가 없는 출발 Place는 422이다.

응답의 각 항목에는 장소 좌표, 총점, 요소별 점수, 추천 이유, 직선거리, 교통 검증 상태, 데이터 제한사항이 포함된다. 후보가 부족하면 확인 가능한 후보만 반환하며 조건 완화를 안내한다.

## 화면 연동

`GET /recommend`의 기존 룰렛 폼 아래에 Phase 3-B 조건 폼을 추가했다. 기존 출발지 검색 좌표를 재사용하며 카테고리·구군·시간·예산·랜덤성·추천 수를 입력할 수 있다. 결과 카드는 점수, 이유, 교통 상태와 제한사항을 표시한다. 기존 Leaflet/OpenStreetMap 구성을 재사용해 실제 DB 좌표만 마커로 표시하며 버스 운행 경로 선은 그리지 않는다.

## 실제 데이터 검증 범위

이번 단계에서는 원본 MySQL(Flyway V4)과 격리 MySQL 모두 연결하거나 변경하지 않았다. 따라서 실제 MySQL 추천 결과와 실제 100번 노선 구간의 추천 점수 반영은 미검증이다. H2 Fixture 결과와 기존 Phase 3-A-2의 격리 DB 검증 결과를 구분해야 한다.

## 데이터 제한 및 Phase 3-C 준비

현재 미완료 항목은 방문 예상시간, 가격/무료 여부, 전체 부산 버스망, 실제 도보거리, 실시간 운행정보다. Phase 3-C는 현재의 `RecommendationResultDto` 후보를 입력으로 재사용할 수 있으나, 여러 장소의 순서를 최적화하려면 장소 간 거리 행렬, 체류시간/운영시간 데이터, 코스 전체 예산의 근거 데이터가 추가로 필요하다. 근거 데이터가 추가되기 전에는 해당 값을 임의 생성하지 않는다.

# 부산 대중교통 경로 API 조사

> 조사 기준일: 2026-10-09  
> 범위: API 선정과 MVP 연동 설계. 이번 단계에서는 API Client나 추천 로직을 구현하지 않는다.

## 1. 목적

City Roulette의 추천 순서를 다음과 같이 정하기 위해, 출발 좌표와 관광지 좌표 사이의 실제 대중교통 경로 및 예상 이동시간을 제공하는 API를 선정한다.

1. 출발 위치를 좌표로 변환한다.
2. 이동 가능한 관광지를 시간 조건으로 걸러낸다.
3. 조건을 만족한 후보 중 하나를 무작위로 추천한다.

현재 `Place`는 nullable `Double latitude`, `Double longitude`를 저장한다. 관광정보 연동에서는 한국관광공사 KorService2의 WGS84 `mapy`를 `latitude`, `mapx`를 `longitude`로 매핑한다. 따라서 별도의 좌표계 변환 없이 ODsay의 X=경도, Y=위도 요청에 사용할 수 있다. 좌표가 없거나 범위를 벗어난 장소는 후보에서 제외해야 한다.

## 2. 요구사항

- WGS84 출발/도착 좌표로 부산 시내 버스·도시철도·도보가 결합된 경로를 검색할 수 있어야 한다.
- 각 후보의 총 예상 이동시간(분)을 얻을 수 있어야 한다.
- 여러 경로가 있으면 MVP에서는 `totalTime`이 가장 작은 유효 경로를 사용한다.
- 전체 관광지마다 외부 API를 호출하지 않고, 호출 전에 근거리 후보를 제한한다.
- API 키는 서버 환경변수로만 주입하고 저장소와 응답에 노출하지 않는다.
- 외부 API 실패, 검색 결과 없음, 일일 한도 소진을 정상적인 실패 상태로 다룰 수 있어야 한다.

### 부산 공공데이터만으로 부족한 이유

부산 버스 API와 도시철도 데이터는 경로 계산에 필요한 원천 정보의 일부를 제공한다. 그러나 이를 이용해 좌표 스냅, 도보 연결, 시간표/노선 그래프, 환승 규칙, 경로 탐색, 총 소요시간 계산을 애플리케이션이 직접 구현해야 한다. 이는 관광지 추천 MVP보다 훨씬 큰 별도 길찾기 엔진 개발 범위다. 따라서 공식 공공데이터는 향후 실시간 정보 보강용으로 남기고, 경로 계산은 전문 API에 맡긴다.

## 4. 최종 선택

MVP의 대중교통 경로 계산 API로 **ODsay 대중교통 길찾기 v1.8**을 선택한다.

- 출발지와 목적지를 WGS84 좌표로 전달할 수 있다.
- 부산 시내의 버스, 지하철, 도보 결합 경로를 받을 수 있다.
- 추천 가능 여부 판단에 직접 필요한 `info.totalTime`을 분 단위로 제공한다.
- 응답 DTO를 필요한 요약 필드만으로 작게 설계할 수 있다.

대학 프로젝트에서 기능 가설을 검증하기에는 적합하지만, Basic 한도로 다수 사용자를 서비스할 수 있다는 뜻은 아니다. 실제 서비스 확장 전에는 유료 요금제, 대용량 API 계약 또는 다른 공급자를 다시 평가한다.

## 5. ODsay 요청 구조

### 대상 endpoint

```http
GET https://api.odsay.com/v1/api/searchPubTransPathT
```

`searchPubTransPathT`는 공식 레퍼런스가 안내하는 대중교통 길찾기 v1.8 endpoint다. Issue 초안의 `https://api.odsay.com/api/searchPubTransPath`는 `/v1`이 빠져 있고 구형 endpoint 이름이다. 공식 문서는 v1.7의 `searchPubTransPathR` 및 더 오래된 `searchPubTransPath`도 설명하지만, 신규 구현은 권장 버전인 v1.8을 기준으로 한다.

### 파라미터

| 이름 | 필수 | MVP 값 | 의미 |
| --- | --- | --- | --- |
| `apiKey` | O | 환경변수 `ODSAY_API_KEY`에서 읽고 URL 인코딩 | ODsay Server API 키 |
| `SX` | O | 출발지 `longitude` | 출발 X좌표, WGS84 경도 |
| `SY` | O | 출발지 `latitude` | 출발 Y좌표, WGS84 위도 |
| `EX` | O | 관광지 `longitude` | 도착 X좌표, WGS84 경도 |
| `EY` | O | 관광지 `latitude` | 도착 Y좌표, WGS84 위도 |
| `OPT` | X | `0` | 추천 경로 정렬 |
| `SearchType` | X | `0` | 도시 내 경로 검색 |
| `SearchPathType` | X | `0` | 버스와 지하철 모두 검색 |
| `output` | X | `json` | JSON 응답 |
| `lang` | X | `0` | 국문 응답 |

키를 제외한 형태의 예시는 다음과 같다.

```text
https://api.odsay.com/v1/api/searchPubTransPathT?SX=출발경도&SY=출발위도&EX=도착경도&EY=도착위도&OPT=0&SearchType=0&SearchPathType=0&output=json&lang=0
```

Spring 백엔드에서 호출하므로 ODsay 애플리케이션도 **Server 플랫폼**으로 등록하고 서버의 공인 IP를 맞춰야 한다. Web 키를 백엔드에서 사용하면 인증 실패가 날 수 있다.

## 6. 필요한 응답 필드

MVP는 전체 응답을 저장하지 않고 다음 필드만 역직렬화한다. 실제 JSON의 이름은 `Info`가 아니라 소문자 `info`다.

| JSON 경로 | 용도 |
| --- | --- |
| `result.path[]` | 검색된 경로 후보 목록 |
| `result.path[].pathType` | 1 지하철, 2 버스, 3 버스+지하철 |
| `result.path[].info.totalTime` | **최종 시간 필터 기준**, 총 소요시간(분) |
| `result.path[].info.totalWalk` | 총 도보 이동거리 |
| `result.path[].info.payment` | 총 요금 |
| `result.path[].info.busTransitCount` | 버스 환승 카운트 |
| `result.path[].info.subwayTransitCount` | 지하철 환승 카운트 |
| `result.path[].info.firstStartStation` | 최초 승차 정류장/역 |
| `result.path[].info.lastEndStation` | 최종 하차 정류장/역 |
| `result.path[].subPath[].trafficType` | 1 지하철, 2 버스, 3 도보 |
| `result.path[].subPath[].sectionTime` | 구간 소요시간 |
| `result.path[].subPath[].distance` | 구간 이동거리 |

경로 목록이 비어 있지 않고 `totalTime`이 유효한 경로들 중 **최소 `totalTime`**을 선택한다. `OPT=0`의 첫 결과는 추천 정렬 결과이지 반드시 수학적으로 가장 짧은 시간이라고 단정하지 않는다. 동일 최소 시간일 때는 첫 경로를 사용해 결과를 결정적으로 만든다.

## 7. 호출량 문제

[ODsay 운영정책](https://lab.odsay.com/doc/totalPolicy)은 조사일 현재 Basic을 개인·학생·5인 이하 스타트업 대상으로 **30회/일** 제공한다고 안내한다. 초당 제한도 있지만 정확한 수치는 공개하지 않는다. 정책은 바뀔 수 있으므로 구현 시작일과 발표 전 다시 확인한다.

관광지 약 351개에 대해 요청마다 351회 호출하는 방식은 금지한다. Basic 30회/일에서는 단 한 번의 추천도 완료할 수 없고, ODsay 정책도 일반 경로 검색을 단일 호출 용도로 설명하며 대용량 경로 검색은 별도 문의 대상으로 둔다.

후보를 10개씩 호출해도 캐시가 없다면 하루 3번, 5개씩이면 최대 6번의 추천 시도에 불과하다. 따라서 Basic은 개발·발표 검증용 한도로 보고 호출 수를 계측해야 한다.

## 8. 후보 사전 필터 전략

두 단계로 처리한다.

현재 1단계는 `GET /api/places/nearby?lat={위도}&lon={경도}&limit=5`로 구현되어 있다. 이 endpoint는 DB의 좌표가 있는 장소를 Haversine 직선거리순으로 정렬할 뿐 ODsay를 호출하지 않는다.

2단계 확인용 `GET /api/places/transit-candidates?lat={위도}&lon={경도}&limit=3`는 가까운 후보마다 ODsay를 한 번씩 호출한다. 기본 후보는 3개, 최대 5개이므로 `limit=3`이면 ODsay 호출을 최대 3회 사용한다. Basic 호출량 보호를 위해 수동 확인은 `limit=1`부터 시작하고 반복 새로고침하지 않는다.

1. **Haversine 사전 필터**
   - 출발 좌표와 좌표가 있는 모든 `Place` 사이의 직선거리를 로컬에서 계산한다.
   - 거리가 가까운 순서로 정렬하여 기본 5개만 남긴다.
   - 후보 수는 설정값으로 두되 Basic 환경에서는 5, 유료/통제된 검증에서만 최대 10을 권장한다.
2. **ODsay 실제 시간 필터**
   - 사전 후보에 대해서만 ODsay를 한 번씩 호출한다.
   - 후보별 최소 `totalTime`을 구하고 최대 편도 이동시간 이하인 후보만 남긴다.

직선거리는 API 호출 대상을 줄이기 위한 근사치일 뿐 최종 이동 가능 여부가 아니다. 강, 산, 환승 구조 때문에 가까운 장소의 대중교통 시간이 더 길 수 있으므로 최종 판단은 ODsay `totalTime`으로 한다.

추가 절감책은 다음 구현에서 검토한다.

- 동일하거나 충분히 가까운 출발 좌표와 동일 목적지 조합을 짧은 TTL로 캐시
- 요청 단위 및 일 단위 호출 카운터와 남은 예산 기록
- 타임아웃, 제한 초과, 결과 없음에는 무제한 재시도 금지
- 여러 사용자가 있는 환경에서는 일일 예산을 넘기기 전에 빠르게 실패

## 9. 추천 알고리즘 초안

MVP의 시간 입력은 **최대 편도 이동시간(분)** 으로 정의하는 것이 가장 단순하다. `totalTime`과 직접 비교할 수 있고 관광 체류시간이나 귀가시간을 임의로 추정하지 않아도 된다.

전체 사용 가능 시간을 입력받는 모델은 후속 단계에서 아래처럼 명시적인 체류시간과 여유시간이 있을 때만 사용한다.

```text
최대 편도 이동시간 = floor((전체 가능시간 - 관광 체류시간 - 여유시간) / 2)
```

추천 흐름:

1. 출발 WGS84 위도·경도와 최대 편도 이동시간을 검증한다.
2. DB에서 유효한 위도·경도가 있는 `Place`를 조회한다.
3. Haversine 직선거리로 정렬하여 가까운 후보 5개를 뽑는다.
4. 각 후보에 대해 ODsay v1.8을 호출한다.
5. 각 응답의 유효 경로 중 최소 `info.totalTime` 경로를 선택한다.
6. `totalTime <= 최대 편도 이동시간`인 후보만 남긴다.
7. 남은 후보 중 하나를 무작위로 선택한다.
8. 장소와 선택된 경로 요약을 반환한다.
9. 후보가 없으면 조건을 늘리거나 출발 위치를 바꾸라는 결과를 반환한다. 전체 관광지 재호출이나 무제한 후보 확장은 하지 않는다.

즉, 무작위 선택은 반드시 `전체 장소 → 거리 후보 → 실제 교통시간 필터` 이후에 실행한다.

현재 MVP의 `GET /api/recommendations/random`은 `availableMinutes`를 출발부터 귀가까지의 전체 사용 가능 시간으로 정의한다. 귀가 경로를 추가 호출하지 않고 `편도 totalTime × 2 + stayMinutes`를 예상 필요시간으로 사용하며, 기본 체류시간은 60분이다. 시간 조건을 통과한 후보 중 마지막에 하나를 무작위 선택한다. 편도 두 배는 실제 귀가시간이 다를 수 있는 근사값이며, 호출량 여유와 캐시가 마련되면 귀가 경로를 별도로 평가할 수 있다.

## 10. 보안

- 키 이름은 `ODSAY_API_KEY`로 정한다.
- 실제 키를 `application.properties`, README, Java 코드, 테스트 픽스처, 로그, 예외 메시지, Git 이력에 넣지 않는다.
- 추후 `.env.example`에는 `ODSAY_API_KEY=your_api_key` placeholder만 둘 수 있다.
- 서버용 키와 등록 공인 IP를 사용하고, 백엔드가 프런트엔드에 키를 전달하지 않는다.
- 요청 URL 전체를 로깅하면 쿼리의 키가 노출될 수 있으므로 키를 마스킹한다.

Client 구현 전에는 ODsay 회원가입, 애플리케이션 생성, **Server 키 발급**, 실행 서버 공인 IP 등록, 최신 정책/한도 재확인, 로컬 비밀 환경변수 설정이 필요하다. 부산 내 대표 출발지와 관광지 1쌍으로 수동 호출하여 응답 구조와 단위를 먼저 검증한다.

## 12. 한계

- Basic 호출 한도가 30회/일로 작아 개발과 시연도 계획적으로 해야 한다.
- ODsay의 예상 이동시간은 경로 탐색용 추정치이며 실시간 버스 대기상황을 완전하게 보장하는 값으로 취급하지 않는다.
- 외부 서비스의 장애, 지연, 정책·스키마·요금 변경에 영향을 받는다.
- 가까운 장소 5개만 먼저 보는 방식은 호출량을 아끼는 대신, 직선거리는 더 멀지만 교통편이 좋은 장소를 놓칠 수 있다.
- 실제 서비스 규모에서는 유료 플랜, 대용량 대중교통 API 또는 다른 공급자를 검토해야 한다.
- ODsay 운영정책의 상표 가이드에 따라 결과 화면 등에 `powered by www.ODsay.com`과 같은 출처 표시가 필요하다.
- 이 조사는 공식 문서 기반 설계 검증이다. 실제 API 키를 발급하거나 인증 호출을 실행하지 않았으므로 부산 표본 응답과 키 플랫폼 설정은 다음 Issue에서 확인해야 한다.

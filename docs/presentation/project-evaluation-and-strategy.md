# City Roulette 웹 프로젝트 평가 및 발표 전략

## 1. 발표의 핵심 결론

City Roulette의 강점은 기능 개수가 아니라 **실제 공공데이터를 안전하게 통합하고,
검증 가능한 정보만 사용해 추천 결과를 만드는 전체 흐름**에 있다.

발표에서는 다음 문장을 중심 메시지로 사용한다.

> 부산 관광 공공데이터 395건을 하나의 장소 DB로 통합하고, 데이터가 부족한 경우에도
> 확인되지 않은 시간이나 비용을 만들지 않는 추천·룰렛 서비스를 구현했습니다.

## 2. 핵심 원리

### 데이터 수집과 멱등성

- 공급자별 API 응답을 공통 `NormalizedPlace` 형식으로 변환한다.
- `(provider, external_id)`로 동일 원천을 식별한다.
- 동일 조건으로 다시 수집해도 Place와 PlaceSource가 중복 증가하지 않는다.
- 다른 공급자의 유사 장소는 자동 병합하지 않고 검토 후보로 남긴다.
- 이미지 라이선스가 불명확하면 대체 이미지를 표시한다.

### Spring Boot 3계층 구조

- Controller는 요청과 응답 형식을 처리한다.
- Service는 추천, 코스 생성, 저장, 수집 규칙을 수행한다.
- Repository는 DB 조회와 페이지네이션을 담당한다.
- 외부 API 수집기는 일반 웹 요청과 분리된 수동 Runner로 실행한다.

### 추천 점수와 데이터 부족 처리

- 카테고리, 직선거리, 다양성, 데이터 품질, 검증된 교통 정보를 0~100점으로 정규화한다.
- 교통을 평가할 수 없으면 교통 점수를 제외하고 나머지 가중치를 다시 계산한다.
- 경로가 없다는 결과를 부산 전체에서 이동 불가능하다는 의미로 사용하지 않는다.
- 시간, 요금, 실제 도로 이동거리는 원천 데이터가 없으므로 생성하지 않는다.

### 룰렛과 재현성

- 추천 점수를 선택 확률에 반영하는 가중 비복원 추출을 사용한다.
- 기본 실행은 새로운 seed로 결과를 다양하게 만든다.
- 같은 입력과 seed를 사용하면 같은 결과를 재현한다.
- 역할 그룹 다양성 보정으로 음식점 등 한 유형이 연속되는 현상을 줄인다.

### 회원 데이터와 보안

- Spring Security 로그인과 CSRF 보호를 유지한다.
- 코스와 즐겨찾기는 인증된 회원 ID를 서버에서 결정한다.
- 다른 회원의 코스 조회·수정·삭제를 차단한다.
- 코스 수정은 version 값으로 오래된 화면의 덮어쓰기를 방지한다.

## 3. 웹프로젝트 평가 관점의 자체 점검

아래 점수는 교수님의 실제 채점 결과가 아니라, 일반적인 웹프로그래밍 프로젝트 기준으로
작성한 자체 점검이다.

| 평가 항목 | 비중 | 자체 평가 | 근거 |
| --- | ---: | ---: | --- |
| 기능 완성도 | 25 | 24 | 검색, 추천, 룰렛, 로그인, 코스 저장, 즐겨찾기, 파일 기능 |
| 웹 구조와 코드 품질 | 20 | 18 | MVC 3계층, DTO, Service 분리, Flyway, 한글 설명 문서 |
| DB 및 공공데이터 활용 | 20 | 20 | 4개 공급자 395건, 출처 분리, 멱등 수집, 라이선스 정책 |
| 보안과 데이터 무결성 | 15 | 13 | 인증, CSRF, 소유권, UNIQUE/FK, 낙관적 잠금 |
| UI·반응형·접근성 | 10 | 9 | Chromium QA, 360~1440px, reduced motion, 빈 상태 |
| 테스트와 시연 안정성 | 10 | 10 | 자동화 테스트 334개, MySQL·브라우저·재시작 검증 |
| 합계 | 100 | 94 | 실제 채점표에 따라 달라질 수 있음 |

### 감점 위험

- 버스 데이터는 100번 노선 일부 20개 정차 구간이라 부산 전체 교통망을 대표하지 않는다.
- 실시간 도착정보, 실제 이동시간, 요금, 운영시간은 지원하지 않는다.
- 지도 타일과 일부 외부 기능은 인터넷 및 API 키에 의존한다.
- 공개 배포보다 로컬 시연 환경에 초점을 맞췄다.

이 한계를 숨기기보다 **검증 범위를 명확히 구분했다는 설계 선택**으로 설명한다.

## 4. 발표에서 강조할 순서

1. 여행 장소를 결정할 때 검색, 지도, 비교가 분산되는 문제를 20초 안에 설명한다.
2. 즉흥 룰렛과 맞춤 코스 추천이라는 두 사용 흐름을 보여준다.
3. 실제 DB 395건과 공급자 4개를 숫자로 제시한다.
4. API 수집, 정규화, 중복 방지, PlaceSource 저장 흐름을 설명한다.
5. 추천 점수와 seed 재현성, 역할 그룹 다양성을 실제 결과와 연결한다.
6. 로그인 후 코스 저장과 즐겨찾기를 시연한다.
7. 테스트 334개와 Chromium QA를 근거로 안정성을 제시한다.
8. 부분 버스 데이터와 시간·요금 미지원 범위를 정확히 밝힌다.

## 5. 발표에서 줄일 내용

- 모든 Entity 필드를 하나씩 읽지 않는다.
- 모든 API 엔드포인트와 환경변수를 나열하지 않는다.
- Phase 1부터 Phase 5까지 작업 이력을 시간순으로 설명하지 않는다.
- 단위 테스트 클래스 이름을 나열하지 않는다.
- 구현하지 않은 전체 버스망이나 실시간 기능을 완성 기능처럼 말하지 않는다.

## 6. 교수님 질문에 대비할 답변

### 왜 Place와 PlaceSource를 분리했나요?

여러 공급자가 같은 장소를 제공할 수 있기 때문이다. 화면에서 사용하는 대표 장소와
원천 식별자, 라이선스, 마지막 동기화 시각을 분리하면 원본 추적과 재수집이 안전하다.

### 왜 유사 장소를 자동으로 합치지 않았나요?

장소명과 주소가 비슷해도 다른 지점일 수 있다. 잘못 합치면 복구가 어려워 확실한
`provider + externalId`만 자동 갱신하고 공급자 간 유사성은 후보로만 기록했다.

### 랜덤인데 왜 같은 결과를 재현할 수 있나요?

고정 seed를 주입할 수 있게 설계했다. 일반 사용에서는 새 seed를 사용하고, 테스트와
오류 재현에서는 같은 seed로 동일 결과를 만든다.

### 추천 점수는 믿을 수 있나요?

점수는 실제 이동시간이나 만족도를 예측하는 값이 아니다. 사용자가 선택한 카테고리,
직선거리와 데이터 품질을 비교하기 위한 정규화된 순위 점수이며 화면에 근거를 함께 표시한다.

### 버스 경로 결과가 없는 장소는 이동할 수 없나요?

아니다. 현재 적재된 버스 데이터가 일부이므로 후보 없음은 적재 데이터 안에서만 후보가
없다는 뜻이다. 추천은 유지하고 교통 정보 확인 필요 상태로 표시한다.

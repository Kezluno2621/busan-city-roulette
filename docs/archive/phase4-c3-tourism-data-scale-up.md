# Phase 4-C-3 부산 관광 공공데이터 단계적 확대 수집

작성일: 2026-10-31 (Asia/Seoul)

## 결론

검증된 Flyway V12, Place/PlaceSource 90/90 격리 DB를 다시 복제하여 네 장소 공급자를 20→50→100건 순서로 확대했다. 첫 50건 시도에서 마지막 페이지의 요청 크기가 20에서 10으로 바뀌면서 페이지 번호 기반 API 오프셋이 겹치는 문제를 발견해 100건 단계로 진행하지 않았다. `PlaceCollectionService`가 모든 페이지에서 고정 pageSize를 사용하고 마지막 페이지에서는 저장 개수만 제한하도록 수정한 후 새 90건 복제본에서 50·100건 단계를 다시 검증했다.

최종 결과는 Place/PlaceSource 395/395, 공급자별 원천 중복 0, FK 고아 0, 기존 90개 Place ID 누락 0이다. 원본 MySQL에는 접근하거나 쓰지 않았다.

## 공급자별 API 조회 범위

확대 모드에서 첫 페이지의 실제 `totalCount`를 확인했다.

| Provider | 실제 reportedTotalCount | 페이지 번호 | 검증 pageSize | 이번 저장 상한 |
|---|---:|---|---:|---:|
| TOUR_API | 2,229 | 1부터 증가 | 20 | 100 |
| BUSAN_ATTRACTION | 213 | 1부터 증가 | 20 | 100 |
| BUSAN_RESTAURANT | 471 | 1부터 증가 | 20 | 100 |
| BUSAN_GALMAETGIL | 85 | 1부터 증가 | 20 | 전체 85 |

페이지 종료는 `pageNo * pageSize >= totalCount`, 빈 페이지, 또는 pageSize보다 짧은 응답으로 판단한다. API 인증·응답·정규화 실패는 모든 단계에서 0이었다. 위 전체 건수는 API가 보고한 값이며 이번 DB 신규 저장 건수와 다르다.

부산푸디투어는 테마 콘텐츠이므로 확대 저장 대상에서 제외했다.

## 확대 모드 안전장치

기본 Runner 제한은 계속 20건이다. 다음 플래그를 명시한 dev 검증 실행에서만 pageSize/limit을 100까지 허용한다.

```text
TOURISM_VERIFICATION_EXPANDED_LIMIT_ENABLED=true
```

확대 모드에서도 DB 지문, 원본과의 분리, Flyway V12, 백업 파일과 SHA-256, 명시적 격리 확인을 모두 통과해야 WRITE_VERIFY가 실행된다.

## 페이지네이션 결함 발견과 수정

최초 50건 단계에서 마지막 요청을 `pageNo=3, pageSize=10`으로 변경했다. 페이지 번호 API는 pageSize도 오프셋 계산에 사용하므로 이전 20건 페이지와 일부가 겹쳤다.

- Dry-run 예상: 공급자별 신규 30, 갱신 20
- 실제 초기 저장: TourAPI를 제외한 부산 API는 신규 20, 갱신 30
- 이상 확인 직후 100건 단계 중단
- 해당 복제본은 증거로 보존하고 새 90건 복제본에서 재시작

수정 후 모든 요청은 pageSize=20을 유지하고, 마지막 응답에서 필요한 10건만 importer에 전달한다. 50건 테스트는 요청 순서 `1:20`, `2:20`, `3:20`을 검증한다.

## 미완료 사항과 Phase 5

- 원본 MySQL에는 V12나 확대 데이터를 적용하지 않았다.
- TourAPI 2,229건, 부산명소 213건, 부산맛집 471건 전체 수집은 수행하지 않았다.

- 실제 브라우저 Leaflet 화면과 회원 UI 수동 검증은 미완료다.

395건 격리 표본 기준으로 페이지네이션, 공급자별 멱등성, 추천·룰렛 안정성이 확인되어 Phase 5 기능 개발은 가능하다. 운영 또는 원본 DB 확대 적용은 별도 백업과 명시적 승인 후 진행해야 한다.
